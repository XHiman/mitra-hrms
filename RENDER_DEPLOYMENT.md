# Deploying MITRA HRMS to Render (Free plan)

## Read this first: Render Free storage is temporary

On the Free web-service plan the filesystem is **erased** on every redeploy, every restart and whenever
the service spins down after about 15 minutes without traffic. That includes the SQLite database,
uploaded documents and any backups stored on the server.

The system is therefore deployed as a **stateless host plus a backup file you keep**:

1. **Before you push** a new version: log in as System Administrator → *Settings and backups → Backup & Restore* →
   **Download Full System Backup**. Keep the ZIP on your own computer (not in the Git repository).
2. Push to GitHub; Render builds and deploys. The new instance starts with an empty database and a fresh admin.
3. Log in as that admin → **Upload & restore a backup** → choose the ZIP → read the summary → confirm twice.
4. Everyone is signed out; sign in with an account from the backup and check the data.

If the service merely sleeps and wakes, the same applies: data is gone until you restore. For anything beyond
a trial, use a paid instance with a persistent disk mounted at `HRMS_INSTANCE_DIR`, or move to PostgreSQL.

## One-time setup

1. Push the repository to GitHub (the `.gitignore` keeps `instance/`, databases, `.env` and backups out).
2. Render → **New → Blueprint** → select the repo. `render.yaml` supplies:

| Setting | Value |
|---|---|
| Runtime | Python (`PYTHON_VERSION=3.12.8`) |
| Branch | `main` |
| Plan | Free |
| Build command | `pip install -r requirements.txt` |
| Start command | `bash render_start.sh` |
| Health check path | `/healthz` |

   Or create a **Web Service** by hand with the same values.
3. When prompted, set **`HRMS_ADMIN_PASSWORD`** (12+ characters, must satisfy the password policy and not contain
   the username). If you leave it unset, a one-time password is generated and printed once in the deploy log.
4. Deploy. Open the service URL and sign in as `admin` (or your `HRMS_ADMIN_USERNAME`). Change the password if
   prompted.

## What `render_start.sh` does

```
python -m flask --app run render-init      # create/upgrade tables; create the first admin ONLY if there are no users
exec gunicorn run:app --bind 0.0.0.0:${PORT:-10000} --workers 1 --threads 4 --timeout 120 ...
```

* `render-init` never loads demo data into a database that already has users. Demo data is loaded only if
  `HRMS_SEED_DEMO=1` **and** the database is empty (do not use this in production).
* One worker is required: SQLite allows one writer and the restore maintenance gate lives in the process.
* Debug mode is never enabled.

## Environment variables

| Variable | Required | Notes |
|---|---|---|
| `HRMS_SECRET_KEY` | yes | Generated by the blueprint. Never put it in Git. Not in backups; a restore never changes it. Keep it stable so sessions and signed tokens survive deploys. |
| `HRMS_ADMIN_PASSWORD` | recommended | Used only when the database has no users. |
| `HRMS_ADMIN_USERNAME`, `HRMS_ADMIN_NAME`, `HRMS_ADMIN_EMP_CODE` | no | Defaults `admin`, `System Administrator`, `SYS001`. |
| `HRMS_SECURE_COOKIES` | no | Default on when `RENDER=true`. |
| `HRMS_TRUST_PROXY` | no | Default on when `RENDER=true` (Render terminates TLS). |
| `HRMS_SEED_DEMO` | no | `1` = fictional demo data into an *empty* DB only. |
| `HRMS_INSTANCE_DIR`, `HRMS_DATABASE` | no | Point at a persistent disk if you have one. |
| `HRMS_SESSION_IDLE_MINUTES` | no | Default 30. |
| `HRMS_RESTORE_MAX_UPLOAD_MB` | no | Default 200. Must fit what the plan's memory/timeouts allow. |
| `HRMS_RESTORE_MAX_UNCOMPRESSED_MB` | no | Default 1024 (zip-bomb guard). |
| `PORT`, `RENDER_GIT_COMMIT`, `RENDER_INSTANCE_ID` | provided by Render | Shown in the Backup & Restore status panel. |

## Pre-deployment checklist

- [ ] Latest **Full System Backup** downloaded and stored outside the repository.
- [ ] Tests pass locally (`python -m unittest discover -s tests`).
- [ ] No `.env`, `instance/`, `*.db` or backup ZIP staged in Git (`git status`).
- [ ] `HRMS_SECRET_KEY` is set on the Render service (do not rotate it casually).

## Post-deployment checklist

- [ ] `/healthz` returns `{"status":"ok"}`.
- [ ] Log in as the admin; **Backup & Restore → System status** shows Database health *OK* and the expected commit.
- [ ] Upload & restore the backup; confirm the summary (users, employees, uploads) matches expectations.
- [ ] After restore, sign in with an account from the backup; spot-check leave balances, an uploaded document and the audit-log verification.
- [ ] Download a fresh backup straight away if you changed anything.

## Limitations on Render Free

* Data lives only until the next deploy/restart/idle spin-down. Backups kept on the server are erased too;
  the history list in the UI is erased with them. Only downloaded ZIPs persist.
* Cold start after idling takes tens of seconds; the daily in-process job only runs while awake.
* SQLite + one worker handles light use only. The restore upload is limited by memory/request timeouts of the plan.
* No automatic scheduled off-site backup exists; download them yourself (consider a calendar reminder).
* A Render Shell is not needed and not relied upon.
